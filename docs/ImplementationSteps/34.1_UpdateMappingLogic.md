# ReportSyncer – SchemaMapper/Config Validator Refactor Playbook（统一 ColumnMapping：合并 Explicit/Added）

> 交付对象：Junior Executor AI（上下文很小，别让它自己“悟”）
>
> 目标：把 `ExplicitMappings`（source→target 映射）和 `AddedColumns`（注入常量/参数）合并为**同一个映射规则结构**，让 `SchemaMapper` 用一套逻辑完成：
> - AutoMapByName（同名自动）
> - 显式指定 source 列
> - 显式注入常量
> - 显式注入 job.parameters
> - 必要时忽略 target 列
>
---

## 0. 背景（为什么要改）

你现在的配置分成两套：
- `ExplicitMappings`：显式指定 target 列来自哪个 source 列
- `AddedColumns`：显式给 target 列一个常量（或将来支持 parameter）

这会导致两个问题：
1. **认知负担**：用户要先决定“这是 Explicit 还是 Added”，但本质上它们都是“针对 target 某列，我要怎么给值”。
2. **实现复杂度**：Mapper 需要维护两套数据结构和冲突规则（谁覆盖谁、同名冲突怎么报错）。

更干净的方案是把它们合并成“统一的 Column Mapping Rule”，以 **TargetColumnName** 为主键，每个 target 列最多一条规则。

改完后：
- `ConfigurationValidator`：只做 YAML 静态可判定的校验（结构合法、参数引用是否声明）
- `SchemaMapper`：拿 schema snapshot 后生成每表 mapping plan，并校验“可插入且必须提供值”的 target 列是否都被满足

## 2. YAML 会怎么变（用户配置变化）

### 2.1 旧结构（你现在的大概样子）
```yaml
columnMapping:
  automapByName: true
  explicitMappings:
    TargetA: SourceA
  addedColumns:
    - columnName: CustomerId
      value: "{CustomerId}"
````

### 2.2 新结构（统一 mappings）

**核心：`mappings` 以 target 列为 key。**

```yaml
columnMapping:
  automapByName: true
  mappings:
    # 1) 显式 source 映射
    TargetA:
      fromSource: SourceA

    # 2) 显式常量
    SourceSystem:
      const: "ERP"

    # 3) 显式参数（来自 job.parameters）
    CustomerId:
      fromParameter: CustomerId

    # 4) 显式忽略（可选，只有你需要）
    SomeOptionalCol:
      ignore: true
```

### 2.3 job.parameters 仍然存在

```yaml
syncJobs:
  - name: "FullJob"
    parameters:
      CustomerId: "42"
```

> 约束：同一个 target 列只能选择一种来源：`fromSource` / `const` / `fromParameter` / `ignore` 互斥。

## 4. Step-by-step Implementation（原子步骤，严格按顺序做）

### Step 1 — 改造 ColumnMappingConfig：合并结构

**目标**

* 删除/废弃 `ExplicitMappings` + `AddedColumns`
* 新增 `Mappings: Dictionary<string, ColumnMappingRule>`

**文件**

* `ReportSyncer.Core/Configuration/ColumnMappingConfig.cs`

**实现要点**

1. 新增 `ColumnMappingRule`（record/class 均可）
2. 在 `ColumnMappingConfig` 中新增 `Mappings`
3. 所有 dictionary 用 `StringComparer.OrdinalIgnoreCase`

**验收**

* 编译通过（此时 loader/validator/mapper 可能还没改完，允许 tests 暂时 fail）

---

### Step 2 — 更新 YAML Loader：把 YAML 新结构映射到 Domain

**目标**

* `YamlConfigurationLoader` 能把 `columnMapping.mappings` 映射成 `ColumnMappingConfig.Mappings`
* 修复“只有部分配置时被吞掉”的问题：只要 YAML 出现 `columnMapping` 就构造 `ColumnMappingConfig`

**文件**

* `ReportSyncer.Core/Configuration/YamlConfigurationLoader.cs`

**实现要点**

1. 找到当前 `MapToDomain()` 里 table 的 columnMapping 映射逻辑
2. 映射规则：

   * `AutomapByName = yaml.AutomapByName ?? true`
   * `Mappings = yaml.Mappings ?? empty`
3. `yaml.Mappings` 每个 entry 构造 `ColumnMappingRule`

**验收**

* 解析一个包含 `mappings` 的 YAML 后，Domain 中 `TableTaskConfig.ColumnMapping.Mappings` 有值

---

### Step 3 — ConfigurationValidator：校验 mappings 结构合法 + 参数引用存在

**目标**

* 提前拦住 90% 的“用户写错 YAML”错误

**文件**

* `ReportSyncer.Core/Configuration/ConfigurationValidator.cs`
* `ReportSyncer.Core/Configuration/ConfigurationErrors.cs`

**需要新增的校验（按顺序实现）**

1. **互斥校验**：对每个 `ColumnMappingRule`，以下字段最多只能启用一个：

   * `FromSource` / `Const` / `FromParameter` / `Ignore=true`
   * 如果启用多个 → error `CFG_MAPPING_RULE_CONFLICT`
2. **空值校验**：

   * `fromSource` 为空字符串 → error
   * `fromParameter` 为空字符串 → error
   * `const` 为 null（但字段存在）→ error
3. **参数引用校验**（你要求的核心）

   * 当 rule 使用 `FromParameter`：必须在 `job.Parameters` 中声明对应 key（用 ignore-case set）
   * 若缺失 → error `CFG_JOB_PARAMETER_MISSING`

**验收**

* 新增单测：mapping 使用 `fromParameter: CustomerId` 但 job.parameters 不包含 CustomerId → Validator 失败

---

### Step 4 — SchemaMapper：消费统一 mappings（替代 explicit+added 两套逻辑）

**目标**

* 对每个 target column 用一套优先级规则生成 mapping
* 当 target 存在“可插入且必须提供值”的额外列时：

  * mappings 能覆盖则 OK
  * 覆盖不了则报错

**文件**

* `ReportSyncer.Core/Schema/Mapping/SchemaMapper.cs`

**核心算法（建议按 target 列遍历）**
对每张表：

1. 读取 config：

   * `automap = tableTask.ColumnMapping?.AutomapByName ?? true`
   * `rules = tableTask.ColumnMapping?.Mappings ?? empty`
2. 对每个 `targetCol` 计算 mapping（优先级必须固定，建议如下）：

   1. **rule.Ignore** → `Ignored`
   2. rule.FromParameter 命中 → `Constant`（值从 job.parameters[rule.FromParameter] 取）
   3. rule.Const 命中 → `Constant`
   4. rule.FromSource 命中 → `OneToOne(sourceCol=rule.FromSource)`
   5. automap==true 且 source 有同名列 → `OneToOne(sourceCol=targetCol.Name)`
   6. policy 允许 extra 且 (targetCol.IsNullable || targetCol.IsIdentity) → `Ignored`
   7. 其它 → error（missing required mapping）

> 备注：你口中的 additional column=“可插入且需要值”。在你现有 schema 元数据缺少 `HasDefault/IsComputed` 的前提下，最小可行判定仍然是：
>
> * required-ish = `!IsNullable && !IsIdentity`

**SchemaMapper 内部还必须做的校验**

* `rule.FromSource` 指向的 source col 不存在 → error
* 从 parameter 取值时 key 缺失 → error（即使 Validator 已做，也要防御）
* 如果 rule 定义了 targetCol，但 target schema 根本没有这个列：

  * 建议：warning 或 error（取决于你想不想严格）。第一轮建议 warning。

**验收**

* 新增/更新测试：target 多一个 NOT NULL 非 identity 列，且 mappings 通过 fromParameter 提供 → OK
* target 多一个 NOT NULL 非 identity 列，且 mappings 未提供 → Fail

---

### Step 5 — Context Injection（CustomerId 默认行为）如何处理

你有两种选择，二选一，别两边都做。

**Option A（推荐，最少魔法）：完全配置驱动**

* 删除 SchemaMapper 里“Application→Reporting 自动注入 CustomerId”的硬编码
* 用户必须在 mappings 里写：

  * `CustomerId: { fromParameter: CustomerId }`

**Option B（保留默认行为但不写死为特殊 mapping 类型）**

* 若 `sourceType==Application && targetType==Reporting` 且用户没有给 `CustomerId` 配 rule：

  * SchemaMapper 在内部临时合成一条 rule：`fromParameter = "CustomerId"`
* 但只有当：target 有 CustomerId 且 source 没有 CustomerId 时才触发

**验收**

* 选了 A：更新 YAML 示例与测试，必须显式配置 CustomerId
* 选了 B：保留旧用例，但“target 没有 CustomerId”不应报错
