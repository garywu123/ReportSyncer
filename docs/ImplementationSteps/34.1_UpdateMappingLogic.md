````markdown
# ReportSyncer – SchemaMapper/Config Validator Refactor Playbook（给 AI Coder 的线性执行手册）

> 目标：把“额外可插入列（target 有、source 没有）怎么处理”从当前的硬编码/不支持配置，升级为**配置驱动**（AutoMap + ExplicitMappings + AddedColumns），并且把**参数引用缺失**尽可能提前在 ConfigurationValidator 阶段拦截。

---

## 0. 背景与动机（为什么要改）

### 现状痛点（基于当前代码）
1. `SchemaMapper` 目前**不读取** `TableTaskConfig.ColumnMapping`（`ExplicitMappings` / `AddedColumns` 完全没被用上），遇到 target 额外列时只能：
   - 若 policy 允许且列是 nullable/identity → Ignored
   - 否则直接报 `TargetColumnMissingInSource`
   这使得 “target 必填额外列需要从参数/常量注入” 这种业务需求无法实现。

2. `SchemaMapper` 有硬编码的 Context Injection（`CustomerId`），逻辑写死且与配置/Validator 脱节。

3. `YamlConfigurationLoader.MapToDomain()` 存在一个结构性问题：
   - 只有在 `addedColumns != null` 时才构造 `ColumnMappingConfig`
   - **仅有 explicitMappings（没有 addedColumns）时，ColumnMappingConfig 会丢失**（映射配置等于没加载）

4. `ConfigurationValidator` 当前没有校验 “mapping 中引用的参数是否存在”，导致很多错误只能运行时才炸。

### 改造后的职责划分（核心思想）
- **ConfigurationValidator**：只做 YAML 静态可判定的校验（结构合法、参数引用是否声明）
- **SchemaMapper**：拿到 schema snapshot 后生成每表的 ColumnMappings，并做“可执行性校验”（是否覆盖 required extra insertable columns）

## 2. YAML 行为变化（改完后用户会怎么写）

### 新增能力：AddedColumns 支持从 job.parameters 引用值（Placeholder）
- 约定格式：`"{ParamName}"` 表示从 `SyncJobConfig.Parameters["ParamName"]` 取值
- 不是 placeholder 的 value 当作字面常量字符串

示例：
```yaml
syncJobs:
  - name: "FullJob"
    parameters:
      CustomerId: "42"
    tables:
      - source: "dbo.Orders"
        target: "dbo.Orders_Tgt"
        columnMapping:
          addedColumns:
            - columnName: "CustomerId"
              value: "{CustomerId}"
            - columnName: "SourceSystem"
              value: "ERP"
````

> 说明：你现有的 `valid-full.yml` 已经包含 `explicitMappings` 和 `addedColumns` 结构，只需在需要“注入参数值”时将 `value` 写成 `{Param}`。

### Step 1 — 修复 YAML Loader：确保 ColumnMappingConfig 不会因为缺少 AddedColumns 而丢失

**目标**

* `ColumnMappingConfig` 只要 YAML 出现了 `columnMapping:`（或显式 mappings/automapByName 配置），就必须被构造出来
* 不允许“explicitMappings-only 配置被悄悄吞掉”

**修改文件**

* `ReportSyncer.Core/Configuration/YamlConfigurationLoader.cs`

**实施要点**

* 在 `MapToDomain()` 的 table mapping 段落，当前逻辑是：

  * `var added = t.ColumnMapping?.AddedColumns?.Select(...)`
  * `if (added != null) mapping = new ColumnMappingConfig(...)`
* 改成：

  1. 先判断 `t.ColumnMapping` 是否为 null
  2. `automapByName = t.ColumnMapping?.AutomapByName ?? true`
  3. `explicitMappings = t.ColumnMapping?.ExplicitMappings`
  4. `addedColumns = t.ColumnMapping?.AddedColumns`（可为空）
  5. 只要 `t.ColumnMapping != null` 就构造 `ColumnMappingConfig`（AddedColumns 为空也照常构造）

**验收标准**

* YAML 中只写 `explicitMappings`（不写 addedColumns）时，Domain 的 `TableTaskConfig.ColumnMapping` 不为 null，且包含 ExplicitMappings。

**建议补充测试（若当前 tests 没覆盖）**

* 在 `ConfigurationValidatorUnitTests.cs` 或新增 loader 单测（若你有 loader test 套件）验证 explicitMappings-only 不丢失。

---

### Step 2 — 新增 Placeholder 解析工具（小而独立）

**目标**

* 统一解析 `{ParamName}` 格式
* 后续 Validator 和 SchemaMapper 共用，不要复制粘贴正则

**新增文件（建议）**

* `ReportSyncer.Core/Configuration/ParameterPlaceholder.cs`

**最小 API（只定义签名，不要写一大坨）**

* `public static bool TryParse(string value, out string paramName)`

  * 返回 true 表示 value 是 `{Xxx}` 形式
  * `paramName` 输出去掉花括号后的名字（保留原大小写或统一大小写都行，但要一致）
* `public static bool IsValidParamName(string name)`（可选）

**规则**

* 只接受 `^{...}$` 单个占位符，不支持拼接（比如 `"foo-{A}"` 先别做，避免 scope 爆炸）
* paramName 允许字母数字下划线即可

**验收**

* 单元测试可放在现有的 validator tests 文件里（写 2-3 个用例即可）

---

### Step 3 — ConfigurationValidator：校验 mapping 中的参数引用是否存在

**目标**

* 当 `addedColumns.value` 是 `{Param}` 时，必须在 `job.Parameters` 中声明该 key，否则抛 `ConfigurationException`

**修改文件**

* `ReportSyncer.Core/Configuration/ConfigurationValidator.cs`
* `ReportSyncer.Core/Configuration/ConfigurationErrors.cs`
* （会用到）`ParameterPlaceholder.cs`

**实现步骤**

1. 在 `ConfigurationErrors.cs` 新增错误工厂方法（示例命名即可）：

   * `MissingJobParameter(string jobName, string paramName, string path)`
   * 建议 code：`CFG_JOB_PARAMETER_MISSING`
2. 在 `ConfigurationValidator.ValidateJobs()` 或 `ValidateTables()`（你现有结构里哪个更合适就放哪）中：

   * 遍历每个 `SyncJobConfig job`
   * 建立 `jobParamKeys` 的 case-insensitive set（`StringComparer.OrdinalIgnoreCase`）
3. 遍历 `job.Tables`：

   * 如果 `table.ColumnMapping?.AddedColumns == null` → skip
   * 对每个 `AddedColumnMappingConfig`：

     * `if ParameterPlaceholder.TryParse(added.Value, out paramName)`：

       * 如果 `jobParamKeys` 不包含 `paramName` → 添加 ConfigurationError（path 精确到：`syncJobs[{jobName}].tables[{source}->{target}].columnMapping.addedColumns[{i}].value`）

> 可选：如果你决定也允许 `ExplicitMappings` 里写 `{Param}`，同样做一次检查（但这会增加语义复杂度，不建议第一轮做）。

**验收**

* 新增/更新单测：当 YAML 写了 `value: "{CustomerId}"` 但 job.parameters 没有 CustomerId，应当在 Validator 阶段报 `CFG_JOB_PARAMETER_MISSING`。

### Step 4 — SchemaMapper：引入 ColumnMappingConfig（ExplicitMappings + AddedColumns + AutoMap）

**目标**

* 让 SchemaMapper 真实使用 `TableTaskConfig.ColumnMapping`
* 当 target 有 required extra insertable column 时：

  * 若能被 explicitMappings/addedColumns 覆盖 → 生成对应 mapping
  * 否则报错（错误码可以继续用 `TargetColumnMissingInSource`，但 message 要指导用户去配置）

**修改文件**

* `ReportSyncer.Core/Schema/Mapping/SchemaMapper.cs`

**核心算法（按 target 列遍历，生成 ColumnMappings）**
对每个 `tableTask`：

1. 读取 mapping config：

   * `automap = tableTask.ColumnMapping?.AutomapByName ?? true`
   * `explicit = tableTask.ColumnMapping?.ExplicitMappings`（case-insensitive）
   * `added = tableTask.ColumnMapping?.AddedColumns`（case-insensitive by ColumnName）
2. 预处理 `added`：

   * 构建 `addedByTargetColName` 字典（key=ColumnName，value=AddedColumnMappingConfig）
   * 检测重复 columnName（重复就 errors）
3. 遍历 `targetTable.Columns`：

   * **优先级建议（必须写死）**：

     1. AddedColumns 命中该 targetColName → 生成 `MappingKind.Constant`
     2. ExplicitMappings 命中该 targetColName → 生成 `MappingKind.OneToOne`（sourceColName=explicit[targetCol])
     3. automapByName==true 且 source 有同名列 → `OneToOne`
     4. policy.AllowExtraTargetColumns 且 (targetCol.IsNullable || targetCol.IsIdentity) → `Ignored`
     5. 其它情况 → error（missing required column）
4. AddedColumns 的 ConstantValue 计算：

   * 若 `added.Value` 是 `{Param}` → 从 `job.Parameters` 取值（case-insensitive）

     * 若取不到：这里也应该 error（SchemaMapper 不依赖 Validator 才能正确工作）
   * 否则：ConstantValue 就是字符串本身
5. Ambiguity/冲突规则（必须做，避免 silent overwrite）：

   * 如果同一 target column 同时被 AddedColumns + ExplicitMappings 覆盖 → error
   * 如果 AddedColumns 想写入某列，而 source/explicit 已经映射该列 → error（除非你明确允许 override，但第一轮别做）
6. 类型兼容：

   * OneToOne 继续用你现有 `IsTypeCompatible()` 校验
   * Constant 类型目前无法做强类型校验（字符串转型不是这里的职责），先跳过

**验收**

* SchemaMapper 能在 “target extra required column + AddedColumns 提供常量/参数” 时成功。
* SchemaMapper 能在 “target extra required column + 无 mapping” 时失败，并给出可行动 message。

---

### Step 5 — Context Injection：从“硬编码 CustomerId 特判”过渡到“默认 AddedColumns 规则”

**目标**

* 保留现有默认行为（Application → Reporting 时自动注入 CustomerId），但不要把它写成独立分支逻辑到处散落

**修改文件**

* `ReportSyncer.Core/Schema/Mapping/SchemaMapper.cs`
* `ReportSyncer.Core/Schema/Mapping/SchemaMappingErrorCode.cs`（看你是否保留旧错误码）

**推荐实现（最小侵入）**

1. 保留 `enableContextInjection` 的条件：`sourceConnection.Type == Application && targetConnection.Type == Reporting`
2. 仅当满足以下条件时才“合成一个隐式 AddedColumn”：

   * target table 有 `CustomerId`
   * source table 没有 `CustomerId`
   * 并且用户没有在 AddedColumns/ExplicitMappings 中显式定义 `CustomerId`
3. 合成后走 Step 4 的 AddedColumns 分支生成 Constant mapping（可继续使用 `MappingKind.ContextColumn` 或统一用 Constant）

**行为变化（必须在测试里体现）**

* 如果 target table 根本没有 CustomerId：**不应该报错**（旧逻辑会报 `ContextColumnMissingInTarget`，建议删除这个强制要求）
* 只有当“需要注入（target 有、source 无）且参数缺失”才报错

## 5. 已知限制（别假装不存在）

* 当前 `ColumnSchema` 只有 `IsNullable/IsIdentity`，没有 `HasDefault/IsComputed`。

  * 所以 “required extra column” 的判定仍然是近似：`!IsNullable && !IsIdentity`
  * 如果你真实库里大量使用 NOT NULL + DEFAULT，这套会误报。
  * 解决方案是下一阶段扩展 `ColumnSchema` 和 `SqlServerSchemaInspector`（不放进本次 refactor，除非你愿意扩大范围）。

```

如果你愿意把 scope 再往前推一步（更正确但工作量更大），我可以再给一份 **Step 8+**：扩展 `ColumnSchema` 增加 `HasDefault/IsComputed` 并更新 `SqlServerSchemaInspector.ColumnsSql` 的 playbook。现在这份先把你“配置驱动映射 + 早期参数校验”这条主线落地。
```
