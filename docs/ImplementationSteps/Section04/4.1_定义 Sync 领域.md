## 2. Logic & Invariants

### 2.1 Rule Set（硬规则，不许“差不多”）

**Source 不可变（Prime Directive）**

* Rule S1: Source 连接上禁止任何 `DELETE/UPDATE/TRUNCATE/DROP`。

**环境安全**

* Rule E1: Prod -> Prod 禁止。
* Rule E2: Source 与 Target 指向同一 DB 禁止（self-sync）。

**Target 删除护栏**

* Rule D1: `preSyncTargetAction=true` 且 **没有 filter** 时，必须 `allowAllDelete=true` 否则 pre-flight 直接 block。
* Rule D2: 预计删除比例超过阈值（`confirmLargeDeletePct`）必须“需要人工确认”。

  * 现实吐槽：你现在的 backend 规范里并没有定义“确认握手”怎么走。只写“pause and require confirmation”是产品愿望，不是工程设计。你要么：

    1. preflight 产出 `NeedsConfirmation` 的结果，让 host/UI 再发一次“确认后运行”；要么
    2. 直接抛 `SafetyViolationException`（带 code=NeedsConfirmation + stats），由 host/UI 捕获后让用户确认并“带 override token”重跑。
  * 后端-only 的最小落地：选方案 2（异常阻断 + 明确信息），不然你会卡在“暂停”这个幻想上。

**数据一致性**

* Rule I1: `IDENTITY_INSERT` 必须严格 ON/OFF 成对，并且 OFF 必须在 finally 执行；OFF 失败是 hard-failure。
* Rule I2: Delete 必须 chunk；Insert 必须 batch/TVP（按 run config）。

**Database Type + Context Injection**

* Rule C1: `Source.Type=Application` 且 `Target.Type=Reporting`：自动注入 Context Column（默认 `CustomerId`，可 per-job 配置），取值来自 Job Parameters。
* Rule C2 (Ambiguity Guard): 在 C1 场景下，如果 Source 表里已经有同名 Context Column，必须 pre-flight fail（Ambiguous Context Column）。
* Rule C3: `Reporting -> Reporting`：不自动注入，按映射规则 pass-through。

**依赖排序与缺失父表**

* Rule FK1: 依赖图只对“本次 job 选中的 target tables 子集”建图。
* Rule FK2: 若选中表依赖未选中父表，pre-flight 必须失败并列出缺失表与依赖关系。
* Rule FK3: 执行顺序强制：Insert Parents->Children；Delete Children->Parents；不信任 UI 顺序。

### 2.2 Error Model（分类必须稳定）

* 配置问题 → `ConfigurationException`
* Schema 不兼容/缺失/依赖错误 → `SchemaMismatchException`
* Safety 规则触发（包括 NeedsConfirmation）→ `SafetyViolationException`
* DB/IO runtime 问题 → `SyncExecutionException`
* 用户取消 → `UserCancelledException`
  （别发明新异常类型来逃避分类。）

### Sprint 10 — Configuration Loader / Validator / Provider

#### 1) 背景（Why）

* 当前系统把 YAML 当作不可信输入，必须在任何 DB 行为之前完成静态校验。

#### 2) 影响范围（What/Where）

* `ReportSyncer.Core.Configuration/*`
* `ReportSyncer.Tests/Unit/Configuration/*`

#### 3) 行为变化（User-facing）

* 无（仅保证错误更早、更明确、分类正确）

#### 4) 设计决策（Rules）

* Rule CFG1: Host 只能通过 `IConfigurationProvider.LoadAndValidateAsync` 获取配置，禁止直接拿 loader。

#### 5) Atomic Steps

**Step 10.1 — 定义配置模型最小闭包**

* 目标：`SyncConfiguration / ConnectionConfig / SyncJobConfig / TableTaskConfig / FilterConfig / SafetyConfig / RunConfig / SchemaPolicyConfig` 属性齐全（与 doc 一致）
* 验收：Unit test 反序列化最小配置与 full 配置成功；字段默认值符合预期。

**Step 10.2 — `YamlConfigurationLoader`**

* 目标：
  * **配置内容错误**统一包装为 `ConfigurationException`（YAML 语法错误、缺字段、enum 错误、未知顶层键）
  * **文件 IO 错误**自然抛出（`FileNotFoundException`、`IOException`），不包装为 `ConfigurationException`
  * 消息包含 path + section hint
  * 支持向后兼容：嵌套的未知属性被忽略（通过 `.IgnoreUnmatchedProperties()`）
* 验收：
  * 坏 YAML 语法 → `ConfigurationException`
  * 缺必填字段 → `ConfigurationException`  
  * Enum 值错误 → `ConfigurationException`
  * 未知顶层键 → `ConfigurationException`
  * 文件不存在 → `FileNotFoundException`（**不是** `ConfigurationException`）
  * 嵌套的未知属性被忽略（允许可选字段和向后兼容）

**Step 10.3 — `ConfigurationValidator`（静态规则）**

* 目标：唯一性、必填、cross-link（job 引用 connection）、阈值范围等。
* 特别：`preSyncTargetAction=true && filter=null && allowAllDelete=false` → `SafetyViolationException`（不是 ConfigurationException）。
* 验收：每条规则都有单测，异常类型不漂移。

**Step 10.4 — `ConfigurationProvider`**

* 目标：组合 Loader + Validator；对外只暴露“已验证配置”。
* 验收：Mock 验证调用顺序；异常透明传播。

#### 6) 测试计划

* Unit：
  * `YamlConfigurationLoader_ValidMinimalConfig_Loads`
  * `YamlConfigurationLoader_UnknownTopLevelKey_ThrowsConfigurationException`
  * `YamlConfigurationLoader_InvalidYamlSyntax_ThrowsConfigurationException`
  * `YamlConfigurationLoader_FileNotFound_ThrowsFileNotFoundException`（验证 IO 错误不被包装）
  * `ConfigurationValidator_PreSyncWithoutAllowAllDelete_ThrowsSafetyViolation`
  * `ConfigurationProvider_CallsLoaderThenValidator`

* Integration：
  * 真实文件加载：最小配置、完整配置、参数占位符
  * 错误分类验证：文件不存在 vs YAML 格式错误 vs 配置验证错误

### Sprint 20 — Schema Inspector / Mapper / Dependency Resolver

#### 背景

* Pre-flight 必须先保证：Source 表存在；Target 表结构 + FK 足够用于计划与执行。

#### 影响范围

* `ReportSyncer.Core.Schema/*`
* `ReportSyncer.Tests/Unit/Schema/*`
* `ReportSyncer.Tests/Integration/Schema/*`（LocalDB）

#### 关键规则

* Rule SCH1: Source Inspect = `ExistenceOnly`；Target Inspect = `Full`。
* Rule MAP1: Context Injection 逻辑在 `SchemaMapper` 层实现（不是 writer 层临时拼 SQL）。
* Rule FK2: 缺失父表必须 fail（列出 missing + dependents）。

#### Atomic Steps

**Step 20.1 — `ISchemaInspector` + `SqlServerSchemaInspector`**

* 目标：从 system catalog 拉 `TableSchema/ColumnSchema/ForeignKeyRelation`。
* 验收：Integration test 能正确识别 identity、PK、FK。

**Step 20.2 — `SchemaMapper`（含 Context Injection）**

* 目标：

  * automap by name
  * added columns（用于注入参数常量）
  * Context Injection：App->Reporting 自动追加 AddedColumnMapping（ContextColumnName）
  * Ambiguity Guard：Source 已有同名列 → `SchemaMismatchException`
* 验收：纯 unit tests 用 fake schema 覆盖所有分支。

**Step 20.3 — `IDependencyResolver`**

* 目标：DAG 拓扑排序 + cycle 检测 + missing upstream tables 检测。
* 验收：

  * `DependencyResolver_SimpleHierarchy_ReturnsInsertAndDeleteOrder`
  * `DependencyResolver_MissingParent_ThrowsSchemaMismatchException`
  * `DependencyResolver_Cycle_ThrowsSchemaMismatchException`

### Sprint 30 — Permission Profiler / Safety Validator

#### 背景

* 你要的是“安全优先”，那就别把安全规则散落在 orchestrator 和 writer 里。集中到 `SafetyValidator`。

#### 影响范围

* `ReportSyncer.Core.Security/*`
* Tests：Unit + Integration（权限需要 DB）

#### 核心决策

* Rule SAFE1: “大删除确认”用 `SafetyViolationException`（code=NeedsConfirmation）先阻断，让 host/UI 二次确认再 run。否则“暂停”只是童话。

#### Atomic Steps

**Step 30.1 — Environment 分类器**

* 目标：实现 `IEnvironmentClassifier`（基于 config tag/命名）用于 prod-to-prod 判定。
* 验收：unit tests 覆盖 `_Prod/_Dev` 等规则。

**Step 30.2 — `IPermissionProfiler`**

* 目标：用安全 no-op/rollback 探测 `CanDelete/CanInsert/CanSetIdentityInsert`。
* 验收：integration tests（不同权限账号或模拟）验证 flags。

**Step 30.3 — `SafetyValidator`**

* 目标：实现 E1/E2/D1/D2/I1 的 gate。
* 验收：unit tests 精确断言异常类型+消息包含关键字段（table、pct、allowAllDelete）。

### Sprint 40 — PreFlightValidator + SyncOrchestrator（Pipeline 落地）

#### 背景

* 不变量：pre-flight fail 就 **绝不允许**触发任何 target DML。

#### 影响范围

* `ReportSyncer.Core.Sync/*`
* `ReportSyncer.Core.Infrastructure/*`（NamedDbContextFactory）
* Tests：Unit（mock pipeline）+ Integration（小规模 e2e）

#### Atomic Steps

**Step 40.1 — `INamedDbContextFactory`**

* 目标：按 connection name 创建 `IDbContext`；未知 connection → `ConfigurationException`。

**Step 40.2 — `PreFlightValidator.ExecuteChecksAsync` 顺序固定**

1. Config 已验证（来自 Provider）
2. Inspect Source（ExistenceOnly）
3. Inspect Target（Full）
4. Schema mapping（含 context injection/ambiguity）
5. Dependency plan（target FK over selected set）
6. Permission profile + Work estimate + Safety validate
   （顺序乱了就会出现“先估算再发现 schema 不存在”的愚蠢浪费。）

**Step 40.3 — `SyncOrchestrator` 生命周期**

* 目标：严格 `PreFlight -> Plan -> Execute(delete+insert) -> JobResult`；dry-run 时禁止 DML。
* 验收（unit）：preflight fail 不调用 runner；dryRun 不调用 writer；cancel 映射 `UserCancelledException`。

### Sprint 50 — Data Writer (Delete/Insert/Identity/TVP)

#### 背景

* 你承诺了 chunk delete + batch insert + identity insert 的“安全批处理”。这部分不在 DB 上跑过就等于没实现。

#### 影响范围

* `ReportSyncer.Core.Sync`（writer/querybuilder/identity）
* Integration tests 必须覆盖真实 DML

#### Atomic Steps

**Step 50.1 — `SqlServerQueryBuilder`（纯 unit）**

* 目标：生成参数化 SQL（select/delete/insert）+ filter 拼接规则（date + key AND）。
* 验收：unit tests 断言 SQL 片段与参数集合正确。

**Step 50.2 — `IdentityInsertManager`（integration）**

* 目标：RAII scope，确保 OFF 一定执行；OFF 失败 → `SyncExecutionException` + fatal log。

**Step 50.3 — `SqlDataWriter`（integration）**

* 目标：

  * Delete：`DELETE TOP(@chunk)` loop，支持 filter
  * Insert：batch/TVP（按 config）
  * 配合 SchemaMappingResult（包含 added/context columns）
* 验收：integration tests 断言实际行数变化与 identity 行为正确。
